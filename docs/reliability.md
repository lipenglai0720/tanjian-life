# 订单与缓存的可靠性设计

[项目首页](../README.md) · [验证报告](../performance/benchmarks/2026-11-14/REPORT.md)

本轮改造围绕两个可以复现的问题展开：异步消息失败后的状态收敛，以及店铺写入后各实例缓存的失效。应用仍为单体，使用现有 MySQL、Redis 和 Guava，不额外引入消息中间件。

## 订单的事实来源与状态

提交成功只代表 Lua 已预扣 Redis 库存并追加 Stream 消息。MySQL 事务提交后才算创建订单。用户查询优先读取自己名下的数据库订单，再读取归属校验后的 Redis 结果。

| 状态 | 含义 | 库存动作 |
| --- | --- | --- |
| PENDING | 已受理，尚未确认落库 | 保留预占 |
| CREATED | 已确认数据库订单存在 | 不再扣减 Redis |
| FAILED | 已确认重复订单或数据库售罄 | Lua 幂等补偿，售罄差异暂停活动 |
| REVIEW_REQUIRED | 尝试耗尽，提交结果可能不确定 | 保留预占，等待核对或同 ID 重放 |

数据库以 `(user_id, voucher_id)` 唯一索引和 `stock > 0` 条件扣减兜底。Redisson 用户与优惠券维度的锁减少竞争；数据库事务负责同时提交库存与订单。重复投递相同 ID 时直接识别既有订单。

消费最多尝试五次（含首次），Pending 至少空闲 30 秒后才能被恢复。分页游标保留在轮询之间，避免首批未到重试时间的消息挡住后面的消息。未知异常达到上限后，原消息、原因和次数写入死信，结果标为待核对，最后 ACK；这几步在同一 Lua 中完成。死信写入失败就不 ACK。已完成或已隔离的同一源消息不会重复补偿或重复隔离。

数据库提交后进程中断时，下一次消费先识别已有订单，补全结果与 ACK。异常不等于事务回滚，因此不能在重试耗尽时直接退库存。`recover_orders.py` 默认只读；显式执行后可确认已落库结果，或沿用原订单 ID 和原预占重放。已经补偿的 FAILED 状态不能被此脚本重新打开。

## 库存键丢失

活动进行中直接从数据库剩余库存初始化 Redis，会漏算尚未落库的预占。检测到缺失后先暂停该活动的受理，等待 Stream 已读未确认与未交付消息清空，确认没有待核对订单，再读取数据库库存和已购用户。初始化脚本会再次检查队列和暂停标记后写入快照。恢复操作不会修改数据库订单。

此实现采用保守的全队列排空检查；其他活动持续有消息时，重建可能延后。单 Redis 没有提供跨 MySQL 的分布式事务。Redis 整库丢失或未持久化的已受理消息消失时，不承诺零丢单。对实际部署需另行配置持久化、备份与恢复流程。

## 店铺写入与失效事件

店铺更新、事件插入由同一个 MySQL 事务提交。提交后立即尝试删除 Redis 缓存并通知各实例；失败事件保留在 `tb_cache_invalidation_event`，后台每秒挑选到期事件，失败后按 1、2、4、8、16、30 秒退避重试。多个实例通过 `FOR UPDATE SKIP LOCKED` 分担事件；进程中断后数据库自动释放锁，其他实例可以重新处理。

事件只执行幂等失效和按当前数据库状态同步 GEO，不把旧的事件载荷覆盖为新店铺内容。重建缓存、更新店铺和处理事件使用同一店铺锁。事件发布成功、数据库完成标记尚未提交时再次执行，只会重复失效。

## 两级缓存的边界

Guava L1 最多 10000 项，最长五秒且不超过 Redis 剩余 TTL。Redis 正值缓存为 30 分钟加 0–20% 随机扰动，空值缓存为 30 秒。冷缓存双重检查与分布式锁保证同一热点不会同时大量回源，每实例数据库回源并发最多 16，等待许可最多 100 毫秒。

失效通知到达或订阅重连时增加本地失效代次，清理相应条目；读取 Redis 前记录代次，填充 L1 前再次核对，防止通知与读取交错后放回旧值。Redis 发布订阅采用至多一次语义，不能代替持久事件。[Redis 官方说明](https://redis.io/docs/latest/develop/use-cases/pub-sub/)

五秒是单个 L1 条目的最长驻留时间。Redis 删除成功、某实例漏收通知时可以靠此过期；Redis 本身仍保留旧值或失效事件重试期间，端到端更新可见时间还取决于事件恢复。系统采用最终一致性，不承诺跨数据库与缓存的强一致读。

取消原进程内布隆过滤器的硬拒绝：它不能自动知道其他实例刚创建的店铺，曾可能把合法 ID 持续判为不存在。当前示例数据规模较小，选择空值缓存与有界回源；需要大规模无效 ID 防护时，应另行设计共享索引、过滤器就绪及恢复协议。

## 诊断与排障

管理 HTTP 服务只监听回环地址，默认端口 9081。`/actuator/tanjian` 提供 L1/L2 命中、回源、丢弃旧填充、订阅重置、失效事件待办与延迟、订单重试和死信计数。耗时计数提供总量与最大值，P95/P99 从 JMeter 原始采样计算；指标标签不放用户、订单、token 或提示词。

优先核对数据库订单、唯一约束和库存，再看结果状态、Stream Pending/lag 与死信。XLEN 包含历史已确认消息，不等同于积压。默认保留历史消息便于核验；演示长时间运行时需结合消费组确认位置制定保留策略。
